## #57 — Deterministik Stacktrace

### Sorun

`makeErrorValue` içinde `trace` alanı (fields[3]) şu an boş string olarak
sabitlenmiş (`interpreter.cpp:18`). Hata yakalandığında `e.trace` her zaman `""`.

Stacktrace üretmek için iki önkoşul gerekiyor:

1. Her `Instruction`'ın hangi kaynak satır/sütuna karşılık geldiği bilinmeli.
2. Throw/panic anında `callStack_` gezilebilmeli ve bu bilgi birleştirilebilmeli.

Şu an `Instruction` struct'ında hiç `SourceLocation` alanı yok, `IRFunction`'da
da satır tablosu yok.

### Değişecek Dosyalar

#### `src/ir/instruction.hpp`

`Instruction` struct'ına kaynak konum alanı ekle:

```cpp
struct Instruction {
    Opcode      opcode;
    int         dest       = -1;
    int         src        = -1;
    int         left       = -1;
    int         right      = -1;
    int         intValue   = 0;
    double      floatValue = 0.0;
    std::string stringValue;
    std::string functionName;
    int         jumpTarget = -1;
    std::vector<int> argSlots;

    // YENİ: Bu talimatı üreten kaynak konum (IRGenerator tarafından doldurulur)
    SourceLocation sourceLoc;

    explicit Instruction(Opcode op) : opcode(op) {}
};
```

`SourceLocation` zaten `src/core/location.hpp`'de mevcut — sadece include ekle.

**Dikkat:** `Instruction` her fonksiyonda çok sayıda oluşturuluyor. `SourceLocation`
içinde `filePath` string'i var — move semantiği kullanıldığından kopya maliyeti
yok ama bellek ayak izi hafif büyür. Kabul edilebilir.

#### `src/ir/ir_generator.hpp` ve `src/ir/ir_generator.cpp`

`IRGenerator`'ın halihazırda AST düğümlerine erişimi var; her düğümde `.loc`
mevcut. `emit*` yardımcı fonksiyonlarına `SourceLocation` parametresi ekle ve
üretilen `Instruction`'a yaz.

Pratik yaklaşım: üst seviye `generate*` metodları AST düğümünün `loc`'unu alır,
iç `emit*` çağrılarına iletir. Tüm `emit*` fonksiyonlarını değiştirmek yerine
sadece `CALL`, `RETURN`, `THROW`, `STRUCT_FIELD_SET`, `ARRAY_GET/SET` gibi
hata-odaklı opcode'lara loc eklemek yeterli — stacktrace için kritik olan
çağrı noktalarıdır.

```cpp
// Örnek — emitCall değişimi
void IRGenerator::emitCall(int dest, const std::string& funcName,
                           const std::vector<int>& args,
                           const SourceLocation& loc) {   // ← eklendi
    Instruction ins(Opcode::CALL);
    ins.dest         = dest;
    ins.functionName = funcName;
    ins.argSlots     = args;
    ins.sourceLoc    = loc;                                 // ← eklendi
    emit(ins);
}
```

#### `src/vm/interpreter.cpp` — `makeErrorValue`

Throw/panic anında `callStack_` gezilerek trace string'i oluşturulur:

```cpp
std::string Interpreter::buildTrace() const {
    std::string result;
    // callStack_ en içten dışa: son frame = fırlatılan yer
    for (int i = (int)callStack_.size() - 1; i >= 0; --i) {
        const CallFrame& f = callStack_[i];
        int ip = f.instructionPointer - 1; // -1: şu an çalışan instruction
        if (ip >= 0 && ip < (int)f.function->instructions.size()) {
            const SourceLocation& loc = f.function->instructions[ip].sourceLoc;
            result += f.function->name + " (" + loc.toString() + ")\n";
        } else {
            result += f.function->name + " (?)\n";
        }
    }
    return result;
}
```

`makeErrorValue` içinde:
```cpp
obj->fields[3] = Value::fromString(buildTrace());  // trace artık dolu
```

#### `src/vm/interpreter.hpp`

`buildTrace()` private metodunu ekle:
```cpp
std::string buildTrace() const;
```

### Dikkat Edilecekler

- `instructionPointer` RETURN/CALL'dan sonra `continue` ile döngü başına dönüyor;
  bu yüzden trace'de `ip - 1` kullanılmalı — aksi halde bir sonraki instruction'a
  işaret eder, hatalı konum çıkar.
- `pendingThrow_` ile `THROW` opcode'u arasındaki fark: `pendingThrow_` set
  edildiğinde `callStack_` henüz unwind edilmemiş olabilir — `buildTrace()`'i
  throw anında çağır, unwind'dan önce.
- `ENTER_TRY` / catch bloğu stacktrace'i temizlemez; `trace` alanı fırlatma
  anının anlık görüntüsü olarak kalır.

### Test Senaryosu

```sqt
int inner() {
    throw Error { line: 1, char: 1, message: "kasıtlı hata",
                  trace: "", code: "E_TEST" };
    return 0;
}

int outer() {
    return inner();
}

int main() {
    try {
        outer();
    } catch (e) {
        print(e.trace);  // "inner (test.sqt:2:5)\nouter (test.sqt:8:12)\nmain (...)\n"
    }
    return 0;
}
```

## #53 — LOAD_GLOBAL/STORE_GLOBAL'ı Modül Kapsamı Olarak Yeniden Çerçeveleme

### Sorun

`IRProgram.globalCount` ve `Interpreter.globalSlots_` "program geneli global"
olarak adlandırılıyor ama anlam olarak "bu dosyanın modül kapsamındaki
değişkenler". Tek dosyada fark yok; birden fazla dosya birleştirildiğinde
slot indeksleri çakışır (`#3` / `#5`).

### Şu An Doğru Olan (Değiştirilmeyecek)

Tek dosya derleme tamamen doğru çalışıyor. Bu plan **büyük refactor değil**,
küçük bir etiket ve altyapı değişikliği.

### Değişecek Dosyalar

#### `src/ir/ir_function.hpp`

`IRFunction`'a `moduleId` alanı ekle:

```cpp
struct IRFunction {
    std::string              name;
    std::string              moduleId;    // YENİ: "dosya.sqt" veya "" tek dosyada
    int                      paramCount;
    int                      slotCount;
    std::vector<Instruction> instructions;
    ...
};
```

#### `src/ir/ir_program.hpp`

`IRProgram`'a per-module global slot sayısı ekle (şu an `globalCount` tek sayı):

```cpp
struct IRProgram {
    std::vector<std::unique_ptr<IRFunction>> functions;
    int globalCount = 0;  // şimdilik tek modül; ileride map<moduleId, int>

    // YENİ: hangi modülün kaç global slotu var
    // Tek dosya: {"", globalCount} — ileride {"a.sqt", 3}, {"b.sqt", 2}
    std::unordered_map<std::string, int> moduleGlobalCounts;
    ...
};
```

#### `src/vm/interpreter.hpp` ve `interpreter.cpp`

`globalSlots_` vektörünü `moduleSlots_` map'ine dönüştür:

```cpp
// Önce:
std::vector<Value> globalSlots_;

// Sonra:
std::unordered_map<std::string, std::vector<Value>> moduleSlots_;
```

`LOAD_GLOBAL` / `STORE_GLOBAL` handler'ları:

```cpp
case Opcode::LOAD_GLOBAL:
    frame.slots[instr.dest] =
        moduleSlots_[frame.function->moduleId][instr.intValue];
    break;

case Opcode::STORE_GLOBAL:
    moduleSlots_[frame.function->moduleId][instr.intValue] =
        frame.slots[instr.src];
    break;
```

GC kökleri de güncellenmeli — `globalSlots_` yerine `moduleSlots_` değerlerinin
tümü `markRoots`'a geçilmeli:

```cpp
// Heap::collect çağrısındaki kök toplama:
std::vector<Value> allGlobals;
for (auto& [id, slots] : moduleSlots_)
    allGlobals.insert(allGlobals.end(), slots.begin(), slots.end());
heap_.collect(allGlobals, callStack_);
```

#### `src/ir/ir_generator.cpp`

`IRGenerator`, fonksiyon üretirken `moduleId`'yi doldurmalı. Şimdilik sabit `""`:

```cpp
IRFunction* fn = new IRFunction(name, paramCount);
fn->moduleId = currentModuleId_;  // IRGenerator'a yeni alan
```

`IRGenerator`'a `currentModuleId_` string alanı ekle, CLI'dan veya kaynak dosya
yolundan set edilsin.

### Dikkat Edilecekler

- `moduleSlots_` map'e geçiş `LOAD_GLOBAL`/`STORE_GLOBAL` her çalıştığında map
  araması yapar. Tek modülde performans farkı önemsiz; ileride sık erişilen modül
  için pointer cache eklenebilir.
- `GC` kök toplama: mevcut `heap_.collect(globalSlots_, callStack_)` çağrısı
  `moduleSlots_` ile güncellenmeli — yoksa global değişkenlerdeki referanslar
  hatalı toplanır.
- Tek dosya senaryosu `moduleId = ""` ile öncekiyle birebir aynı davranır —
  regresyon riski yok.

### Test Senaryosu

Tek dosyada mevcut testlerin tamamı geçmeli. Çoklu dosya testi modül sistemi
issue'ları (#3/#4/#5) tamamlandığında yazılacak.

## #54 — Symbol Struct'ına `sourceModule` Alanı

### Sorun

`Symbol.definitionLoc.filePath` ile modül dolaylı bilinebiliyor ama cross-module
çözümleme, LSP ve hata mesajları için birinci sınıf `sourceModule` alanı gerekli.

### Değişecek Dosyalar

#### `src/symbol/symbol.hpp`

```cpp
struct Symbol {
    std::string                 name;
    SymbolKind                  kind = SymbolKind::Variable;
    Type                        type;
    std::string                 sourceModule;   // YENİ: "dosya.sqt" veya ""
    SourceLocation              definitionLoc;
    std::vector<SourceLocation> references;
    Scope*                      scope     = nullptr;
    bool                        isBuiltin = false;
};
```

#### `src/symbol/symbol_table.hpp` — `define()` metodu

`define()` çağrısında `sourceModule` set edilmeli:

```cpp
Symbol* define(const std::string& name, SymbolKind kind, Type type,
               SourceLocation loc, const std::string& module = "") {
    ...
    sym->sourceModule = module;
    ...
}
```

#### `src/symbol/symbol_collector.cpp`

`SymbolCollector`'a `currentModule_` alanı ekle, `define()` çağrılarına ilet:

```cpp
class SymbolCollector {
    ...
    std::string currentModule_;  // YENİ: CLI'dan set edilir
    ...
};
```

`define()` çağrıları `currentModule_` parametresiyle güncellenir.
`isBuiltin` sembolleri için `sourceModule = "__builtin__"`.

#### `src/cli/commands/symbols.hpp`

JSON çıktısına `sourceModule` alanı ekle:

```cpp
obj["sourceModule"] = sym->sourceModule.empty() ? "<main>" : sym->sourceModule;
```

#### `src/diagnostic/diagnostic.hpp` (ilerisi için hazırlık)

E001 "tanımsız değişken" hint'inde ileride: sembol başka modüldeyse
`"'counter' tanımlı değil — 'a.sqt'de var, import edilmedi"` mesajı üretilebilir.
Şimdilik kod değişmez; altyapı hazırlanır.

### Dikkat Edilecekler

- `sourceModule` boş string olduğunda davranış öncekiyle özdeş — kırıcı değişiklik yok.
- Builtin `Error` struct alanları `SymbolCollector::seedBuiltins`'te tanımlanıyor;
  buraya `sourceModule = "__builtin__"` eklenmeli.
- `SymbolTable::allSymbols()` döndürdüğü listeyi değiştirmiyor — JSON komutları
  bu listeyi okur, `sourceModule` alanı zaten orada olacak.
- #53 ile bağlantı: `IRFunction::moduleId` ile `Symbol::sourceModule` aynı stratejiyi
  kullanmalı (`""` veya dosya yolu) — ileride cross-module çözümlemede tutarlılık.

### Test Senaryosu

`saqut symbols dosya.sqt` çıktısında her sembolde `sourceModule` alanı görünmeli.
Builtin semboller `"__builtin__"`, kullanıcı sembolleri `"dosya.sqt"` (veya `""`
tek dosya modunda).
