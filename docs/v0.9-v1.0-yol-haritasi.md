# saQut 0.9.0 → 1.0.0 Kanıt Odaklı Yol Haritası

**Durum:** Ürün kapsamı kabul edildi; iş paketleri henüz tasarlanmadı  
**Tarih:** 2026-07-25  
**Dayanak:** ADR-042 ve v1.0 Kapsam Bildirgesi

## 1. Baseline

`0.8.0` yayımlanmış tarihsel baseline'dır. Bu yol haritası 0.8.0'ı yeniden
tanımlamaz. Eski release'te bulunan veya bulunduğu iddia edilen özellikler,
0.9/1.0 için güncel kaynak ve binary üzerinde yeniden kanıtlanmadıkça yeni
release sözleşmesine taşınmaz.

## 2. 0.9.0 — VM ve veri işleme preview

0.9.0'ın amacı yeni mimarileri kilitlemek değil, ürün sahibinin VM üzerinde
anlamlı veri-işleme programları yazabildiği ilk güvenilir geribildirim
baseline'ını oluşturmaktır.

### Kapsam

- VM tek normatif çalıştırma yolu.
- `run`, `check`, `ast`, `ir`, `symbols` komutlarının tanımlı temel yüzeyi.
- XML/JSON ayrıştırıcı ve CPU ağırlıklı algoritmik CLI doğrulama programları.
- Basit VM GC'nin varsayılan açık, tekrar çalışan ve gözlenebilir olması.
- Diagnostic exit-code/stdout/stderr davranışının temel matrisi.
- #134, #135, #136 ve #114 gibi doğruluk iddialarının temiz build ile yeniden
  doğrulanması.
- LSP ve DAP için v1 desteklenen yetenek matrisinin ürün sahibince kabulü;
  uygulanmış alt küme varsa preview olarak protocol-level ölçümü.
- Mevcut dar host-call yüzeyiyle yetinme; yeni generic FFI garantisi yok.

### 0.9.0 çıkış kanıtı

- Kaynak commit'i ve build komutu kayıtlıdır.
- VM doğrulama programlarının beklenen davranışı sürümlü fixture'lardadır.
- GC stres senaryosunda birden fazla collection ve canlı kök koruması
  gözlenmiştir.
- Public CLI'da stub boş başarı yoktur; 0.9'da desteklenmeyen komut açıkça
  unsupported olur veya görünmez.
- Bilinen eksikler release notunda dürüstçe listelenmiştir.
- JIT varsa `[EXPERIMENTAL]`; sonucu 0.9 başarısı olarak sayılmaz.

### 0.9.0 kapsam dışı

- AOT ve executable packaging;
- production host entegrasyonu;
- generic native FFI;
- public concurrency;
- JIT feature parity;
- production-grade GC;
- bütün LSP/DAP protokolü.

## 3. 1.0.0 — Tooling ve host entegrasyonu Feedback MVP

1.0.0'ın amacı ürün sahibinin dili gerçek araçlarda deneyip v1.x/v2 kararlarına
veri üretmesidir.

### Zorunlu tooling

- `run`
- `check`
- `ir`
- `ast`
- `symbols`
- `lsp`
- `dap`

Her komut için desteklenen yetenek, input, output, diagnostic, exit-code ve
unsupported davranış matrisi bulunur. LSP/DAP yalnız ilan edilen protokol
alt-kümesinden sorumludur.

### Host/FFI doğrulama hedefleri

- dosya ve klasör otomasyonu;
- seçilmiş SQLite bağlayıcısıyla temel veritabanı işlemi;
- seçilmiş sıkıştırma bağlayıcısıyla sıkıştırma/açma;
- blocking TCP ile tek süreçli mini Redis benzeri kanıt programı.

Bu hedefler implementasyona başlamadan önce ayrı ürün kararlarına bölünür:

- hangi API çağrıları public;
- capability adı ve default-deny davranışı;
- path/encoding/platform semantiği;
- native bağımlılığın dağıtımı ve sürümü;
- hata tipi, diagnostic kodu ve exit davranışı;
- kaynak/bağlantı kapatma modeli.

Ürün sahibi generic native FFI'yi ayrıca seçmedikçe yalnız curated binding
tasarlanır.

### 1.0.0 çıkış kanıtı

- Yedi zorunlu yüzeyin kabul edilmiş matrisindeki her madde tracked testlidir.
- Gerçek program senaryoları güncel release candidate ile çalıştırılmıştır.
- Stub komut ve sahte başarı yolları CLI/help'ten kaldırılmıştır.
- Basit VM GC sözleşmesi doğrulanmıştır.
- JIT bütün yüzeylerde experimental, concurrency public yüzeyde yoktur.
- Desteklenen platformlar ürün sahibi tarafından seçilmiş ve CI'da
  kanıtlanmıştır.
- Release artifact'ı kaynak commit'i, build logu, test raporu ve checksum ile
  izlenebilir.
- Dokümantasyon yalnız desteklenen davranışı anlatır.

## 4. Karar kapıları

Aşağıdaki işler ajan tarafından varsayımla çözülemez:

1. **Platform matrisi:** İlk v1 artifact'ları hangi OS/mimarilerde destekli?
2. **LSP matrisi:** Hangi method/capability'ler v1 sözleşmesinde?
3. **DAP matrisi:** Breakpoint, step, stack, scopes ve evaluate içinden hangileri?
4. **String semantiği:** İndeks byte mı, Unicode code point mi; invalid UTF-8?
5. **Host yüzeyi:** Dosya, process, env, TCP, SQLite ve compression için tam API.
6. **Capability UX:** İzin bayrakları, default deny ve error davranışı.
7. **Kaynak yaşam döngüsü:** Dosya/socket/database handle kapatma modeli.

Başmimar bu kapılarda seçenekleri ve maliyeti sunar. Ürün sahibi karar vermeden
PM bunları implementation task'a dönüştüremez.

## 5. Milestone'a alma kuralı

Bir iş yalnız şu koşullarda 0.9 veya 1.0 milestone'una alınır:

- doğrudan yukarıdaki çıkış kriterlerinden birini karşılar;
- kullanıcıya etkisi tanımlıdır;
- acceptance testi yazılabilir;
- kapsam dışı sınırı vardır;
- bağımlı ürün kararları verilmiştir.

“Gelecekte lazım”, “mimari daha temiz”, “hızlı olmalı” veya “diğer dillerde var”
tek başına milestone gerekçesi değildir.
